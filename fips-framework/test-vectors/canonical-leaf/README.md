# canonical-leaf test vectors

Reproducible inputs and expected outputs for the FIPS-manifest
canonical-leaf format defined in `../../spec-canonical-leaf.md`.

Each subdirectory is one vector with the following layout:

```
<vector-name>/
  fixture/                   The directory tree used as --source-dir
  pubkey.pem                 The publisher's ML-DSA-87 public key
  metadata.txt               --domain, --label, --now, --validity-days, …
  signing-input.json         Canonical form with signature := ""
                             — deterministic, byte-reproducible
  signing-input.sha256       SHA-256 of signing-input.json
  leaf.bin                   One specific signed leaf (0x02 || canonical_json)
                             — the signature in this file is from one
                               run; ML-DSA-87 signing here is randomized,
                               so re-running produces a different sig
  verdict.txt                ACCEPT or one of the rejection reasons
                             from spec §"Server-side validation order"
```

## What's deterministic, what isn't

- **`signing-input.json` is byte-exact** across runs given the same
  `metadata.txt` parameters and the same `fixture/` contents.  The
  SHA-256 in `signing-input.sha256` is a stable identifier for that
  canonical form.  Verifiers SHOULD compare this file byte-for-byte
  against their own canonicalization output.
- **`leaf.bin`'s signature is *not* reproducible.**  wolfCrypt's
  default ML-DSA-87 signing path is randomized.  Two runs with the
  same input produce two byte-different signatures, both valid under
  the same public key.  Use `leaf.bin` for verifying-flow tests
  (does my verifier accept this signature under `pubkey.pem`?), not
  for signing-flow byte-equality tests.

If a future deterministic-sign path is added (FIPS 204 §3.4 supports
it), `leaf.bin` will become byte-stable too and this caveat goes
away — at which point the SHA-256 of `leaf.bin` should be added to
each vector's `metadata.txt`.

## Regenerating a vector

The `signing-input.json` half regenerates with:

```
fips-manifest-submit --domain factsorlie.com --label <L> \
                     --package <P> --version <V> \
                     --source-dir <vector>/fixture \
                     --now <epoch> --validity-days <N> \
                     --out /tmp/leaf.tmp
python3 -c "
import json, sys
data = open('/tmp/leaf.tmp', 'rb').read()
assert data[0] == 0x02
m = json.loads(data[1:].decode())
m['signature'] = ''
print(json.dumps(m, sort_keys=True, separators=(',', ':'), ensure_ascii=False),
      end='')
" > <vector>/signing-input.json
```

The `leaf.bin` half can be regenerated by re-running
`fips-manifest-submit --out <vector>/leaf.bin` with the same args
— but the resulting signature WILL differ, which is fine.

## Negative vectors (planned, not yet present)

Per `spec-canonical-leaf.md` §"Conformance test vectors", we want
hand-crafted negative cases under separate subdirectories
(`neg-unsorted-keys/`, `neg-trailing-newline/`, `neg-slash-escape/`,
`neg-duplicate-key/`, `neg-bad-path-traversal/`, …).  These will
land alongside `fips-manifest-verify` in step 4 of
`../README-implement.md` so we have a verifier to exercise them
against.
